# verif — Фаза A (интервью) и Фаза B (применение)

Читается на Шаге 7, когда пользователь выбрал разбор находок. В default-режиме
(без `--json` / `--report-only` / `--only`) обе фазы обязательны.

## Фаза A: Интервью по находкам

Только в default-режиме. Работает по `$FINDINGS_OUT` (дедуп уже сделан в Arb-1) + `$ARBITER_OUT` (оценки арбитра, если доступны).

### A2. Порог объёма

Если находок > 20 — сначала спроси через AskUserQuestion: «N находок — это ~N/4 экранов по 4 вопроса. Обработать только critical+high (M штук) или все?» Опции: «Только critical+high» / «Все находки». Дальше работай с выбранным подмножеством; невыбранные находки фиксируются в decisions как `skipped`.

### A3. Интервью — батчами до 4 находок за вызов

Сортировка: по `adjusted_severity` арбитра (при недоступном арбитре — по severity находки): critical → high → medium → low. Разбить на батчи по 4. Один вызов AskUserQuestion = один батч = до 4 questions.

Каждый question:

- `header`: `[CRIT] F1` / `[HIGH] F2` / `[MED] F3` / `[LOW] F4` (≤12 символов; severity = adjusted_severity арбитра, если есть).
- `question` — структурированный текст, ~6–12 строк:
  - **Суть** — title + сжатое body (1–2 предложения).
  - **Почему** — причинно-следственная связь: «если оставить как есть → произойдёт X, потому что Y». Выводить строго из body/recommendation/evidence находки.
  - **Пример** — один простой конкретный пример: сценарий проявления проблемы или mini before→after. Только если выводится из материала находки; если нет — блок опустить, НЕ выдумывать.
  - **Арбитр** — из оценки арбитра: rationale + cross_check (если есть); метки Verifier A/B/C деанонимизировать обратно в codex/fable/grok по маппингу из Arb-2. Если `refuted: true` — плашка первой строкой: «⚠ Опровергнуто арбитром: {refuted_reason}».
  - **Мета** — `file:line_start` (или TARGET_PATH если `file` = null), sources (провайдеры через «+»), severity (адж.), confidence.
- `options` — рекомендованная опция ПЕРВОЙ с пометкой «(Recommended)»:
  - Арбитр доступен: `recommendation: apply` → первой «Применить (Recommended)»; `skip` → первой «Пропустить (Recommended)»; `discuss` → обе опции без пометки (порядок: Применить, Пропустить); `refuted: true` → первой «Пропустить (Recommended)» независимо от recommendation.
  - **A3-fallback (арбитр недоступен / id не покрыт):** `claim_type = speculation` ИЛИ `confidence < 0.5` → первой «Пропустить (Recommended)»; иначе → первой «Применить (Recommended)».
  - «Применить» — description: суть recommendation + главный плюс применения.
  - «Пропустить» — description: главный риск/минус пропуска (для слабых/опровергнутых — почему пропуск оправдан).
- «Other» добавляется автоматически: текст пользователя = custom-инструкция (применять по ней, а не по recommendation).

Guard против галлюцинаций: блоки «Почему», «Пример» и «Арбитр» строить ТОЛЬКО из полей находки и оценки арбитра (body, recommendation, evidence_urls, rationale, cross_check, refuted_reason) — ничего не досочинять сверх них.

После всех батчей → A4.

### A4. Фиксация решений

Записать `$DECISIONS_OUT` (Write или jq) — массив объектов:

```json
[{"id": "F1", "title": "...", "sources": ["codex","grok"], "severity": "high",
  "file": "/abs/path.md", "decision": "applied|skipped|custom",
  "custom_instruction": "...",
  "arbiter_recommendation": "apply|skip|discuss|null",
  "refuted": false}]
```

`custom_instruction` — только при decision `custom`; `arbiter_recommendation`/`refuted` — null/false при недоступном арбитре. Если ВСЕ решения `skipped` → пропустить Фазу B и вывести финальную сводку.

## Фаза B: Параллельное применение

1. **Группировка**: одобренные находки (`applied` + `custom`) сгруппировать по целевому файлу (`finding.file`, при `null` — TARGET_PATH). Один файл = один субагент — конфликтов записи нет.
2. **Запуск**: все субагенты в ОДНОМ сообщении (параллельный fan-out). Инструмент субагентов — `Agent` (в других сборках — `Task`), `subagent_type: general-purpose`, model НЕ указывать (наследуют модель сессии).
3. **Промпт субагента**:
   - абсолютный путь целевого файла;
   - список находок этого файла: id, title, body, recommendation (для `custom` — custom_instruction вместо recommendation), line_start/line_end;
   - правила: применить минимальные точечные правки строго по recommendation/инструкции; НЕ трогать другие файлы; НЕ рефакторить и не «улучшать» соседний текст; если находка неактуальна (строки сместились, проблема уже исправлена, рекомендация неприменима) — пропустить и отметить причину;
   - вернуть отчёт: по каждому id — `applied` или `skipped: <причина>`.
4. **Сводка**: собрать отчёты субагентов и вывести финал:
   - consensus verdict;
   - итог интервью: сколько applied / skipped / custom (и сколько находок арбитр опроверг);
   - применение по файлам: что применено, что пропущено и почему;
   - пути к артефактам, включая `AI/verif/{BASE}--decisions.json`.
